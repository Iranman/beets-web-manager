## Immediate Contradictions / Risks Found

- Album/RG identity is partly guarded by `matching_contract`, but candidate ranking can still be produced by independent album AI, folder preflight, playlist placement, or release resolver formulas before the shared contract vetoes or explains anything.
- Track matching exists in at least four forms: app `_best_album_track_match`, backend `mb_alignment`, `track_align`, and playlist/submission-specific matchers. Only some are one-to-one; none provides a single shared evidence object for all callers.
- AcoustID status vocabularies differ by workflow (`match/mismatch/none`, `confirmed/mismatch/unverified`, `acoustid_verified`, `review_required/no_acoustid_result`, release-hit aggregates). Missing/unavailable/no-result/conflict are not represented consistently.
- Numeric confidence gates differ: AI batch high/medium gates, album/playlist `0.70`, preflight `0.82/0.72`, cleanup `0.62/0.90`, submission artist `95`, confirmed import `0.82/0.96`.
- Candidate generation and candidate scoring are mixed in several helpers. MusicBrainz search helpers rank editions, app AI formulas rank identity candidates, and preflight independently recalculates coverage.
- Fresh reviewed imports and existing/reimported material correctly use different trust models today, but their alignment/evidence implementations diverge rather than sharing policy primitives.

### Session 3: playlist unattended-write fix

The prior session's own analysis of *why* this looked unfixable was itself re-examined, not trusted -- and it was wrong on two points, found by re-tracing the actual write path from scratch: (1) the write is not a local `INSERT INTO albums` the Web Manager performs -- `_playlist_find_or_create_album_row` (that local-SQL function) has **zero callers**, confirmed by search; the real write is engine-side IPC (`beets_client.place_playlist_imported_item()` -> `/playlists/place-imported` -> a real `UPDATE items` plus `beet write`/`beet move` against the actual audio file). (2) `evaluate_release_group_candidate()` does *not* actually require an embedded trust model workaround for the single-track case -- passing only the **one specific target track** (not the candidate release's whole tracklist) as the candidate's `tracks` list makes the existing `complete_alignment` concept mean exactly what a single-track placement can honestly claim, and the existing `existing_library` trust model's CONFIRMED path (validated Release Group + complete alignment via a hard per-track identity positive) already fires correctly with zero new trust-model code.

Fix: `_playlist_auto_placement_allowed()` deleted; both call sites now build a single-track probe/target pair and gate on `_playlist_canonical_placement_evidence(...).can_auto_accept()`. `_playlist_album_tag_release_placement` (pure text search, previously never fingerprinted at all) now performs a real `_acoustid_lookup_cached()` lookup before it can auto-place -- it gained the missing evidence path rather than losing the ability to auto-place, per the standing instruction not to fix this by disabling the feature. `_playlist_resolve_album_placement`'s recording loop already gathered AcoustID-sourced candidates first; it now actually feeds them into the canonical evaluator instead of only using `_source == "acoustid"` as an untyped ranking proxy.

Verified in both directions: the exact legacy-vulnerable shape (strong text match, zero fingerprint evidence) now requires review; the legitimate positive case (AcoustID confirms the specific recording) still auto-places; AcoustID confirming a *different* recording than the text match selected produces a hard `CONFLICT`, never auto-acceptable regardless of text score. `tests/test_playlist_pipeline.py` reproduces the deleted legacy formula inline to document/prove the removed vulnerability, asserts the function is genuinely gone from `app.py` (not merely unused), and adds a second test proving the three outcomes above against the real replacement function via AST extraction. Full backend suite: 3122 passed, 0 failed, 146 skipped, 514 subtests. ARCH-003 unchanged (437 entries, 0 unresolved -- pure evaluation logic, no new mutation sinks).

Also added this session: three regression tests for ARCH-002 Part 6 (3+ competing local files with identical titles, resolved correctly by the real global min-cost assignment, proven order-invariant across all 6 permutations, and proven to leave a genuine extra file unmatched rather than force it onto an already-claimed target).
