# Architecture

This document describes the architecture that exists today and the intended direction. It does not claim that the intended architecture is complete.

## Non-Negotiable Rules

These are standing product/architecture invariants, not aspirations. Each is backed by an Architecture Decision Record under `docs/adr/` and, where practical, a regression test — see the linked ADR for full context and consequences.

- **Beets Web Manager builds on stock Beets; it does not build Beets.** The sole authoritative Beets runtime is the published `lscr.io/linuxserver/beets` image, run as its own container. Web Manager provides the UI, workflow orchestration, job tracking, and audit/rollback state, and talks to that container only over HTTP — never a local Beets Python import, a control-agent process, a Docker socket, `docker exec`, or a custom Beets image. (`docs/adr/0001-beets-remains-library-backend.md`)
- Beets remains the library backend and source of library mutations; the app does not grow a parallel music-library database. (`docs/adr/0001-beets-remains-library-backend.md`)
- MusicBrainz and AcoustID are the primary identity evidence. The canonical album-level identity is the MusicBrainz release-group ID (`mb_releasegroupid`); a release ID (`mb_albumid`) is edition-level secondary data and must never be substituted where a release-group ID is required. (`docs/adr/0002-release-group-id-is-canonical-album-identity.md`)
- AI is optional and untrusted. It may rank or explain candidates already found through deterministic sources; it must not invent an identity and treat it as verified, and its unavailability must never stop MusicBrainz/AcoustID matching. (`docs/adr/0003-ai-is-optional-and-not-source-of-truth.md`)
- No silent library mutations. Any move, rename, merge, delete, tag write, replacement, or artwork write requires the controlled preview/apply/audit/recovery workflow in `backend/transaction_engine.py`. (`docs/adr/0004-library-mutations-use-controlled-workflow.md`)
  - **One documented exception: playlist pre-import tag hints.** `composite_workflows.write_staging_tags` (reached only through `write_tags`, from `playlist_service`'s playlist-download tag stamping and enrichment, which `acquisition_service`'s playlist download matching also calls, always before the download is imported) writes `title`/`artist`/`albumartist`/`album`/`year` hints with `mediafile` straight into the downloaded file. It exists because playlist downloads (slskd) often carry no or wrong tags, and Beets' importer needs a usable artist and title to find MusicBrainz candidates. It is allowed only on a regular file under a staging root (the downloads root or `<data dir>/playlist_staging`), never under `MUSIC_ROOT` or on protected Web Manager data, with no symlinked path component and no second hard link (a hardlink made for seeding would share the library file's contents); the file is opened fd-relative with `O_NOFOLLOW` and must still be the entry that was validated, otherwise it raises `ValueError` and nothing is written. These files are not in the library yet: Beets' importer still does the real tagging from MusicBrainz when it imports them, and every tag write to a library file goes through Beets. (Tests: `tests/test_staging_tag_writes.py`.)
- Long-running operations use the shared job infrastructure (`job_engine.py`) rather than ad hoc background threads or bespoke checkpoint logic. (`docs/adr/0005-long-running-operations-use-shared-job-infrastructure.md`)
- Ambiguous or conflicting evidence goes to review; destructive actions require stronger evidence than suggestions.
- Never expose secrets in logs, API responses, frontend state, or committed files.

## Current Main Components

- `beets` (Stock Beets Container): Standard upstream LinuxServer Beets container (`lscr.io/linuxserver/beets:latest`). Owns `/config/config.yaml`, the authoritative `/config/musiclibrary.blb` database, and all `/music` writes. Runs the built-in `web` plugin (read-only HTTP API) and the bundled `webmanager` integration plugin (the only mutation surface Web Manager is allowed to call), both on its own internal `:8337`.
- `beets-web-manager` (Web Manager Container): Production web application built from `Dockerfile`. Has no local Beets Python runtime (`requirements.txt` does not install `beets`) and performs zero local Beets database or media-file mutation. Serves the browser UI and its own API on port 8337, executes background jobs, and talks to stock Beets exclusively through `backend/beets_adapter.py`.
- `app.py`: application glue only (~570 lines since ARCH-001, v0.1.31) — creates the Flask app, request hooks (auth/CSRF/rate limits), security headers, error handlers, static/SPA serving and health, and loads the route modules. Every moved name still resolves as `app.<name>`. See `docs/arch001_service_decomposition.md`.
- `routes_library.py`, `routes_cleanup.py`, `routes_import.py`, `routes_playlist.py`, `routes_acquisition.py`, `routes_maintenance.py`, `routes_system.py`: route families moved out of `app.py`; HTTP handlers over the owned services.
- `backend/*_service.py` (+ `app_runtime.py`, `serializers.py`, `pending_review_store.py`, `library_cache.py`): owned services, strictly layered (a service imports only lower layers; nothing under `backend/` imports `app.py`). Layer order and ownership: `docs/arch001_service_decomposition.md`, `docs/arch001_app_ownership.json`.
- `routes_jobs.py`: split route module for `/api/jobs/*` job listing, lookup, and cancellation.
- `routes_lidarr.py`: split route module for Lidarr/wanted endpoints.
- `routes_setup.py`: split route module for setup, authentication, and configuration checks; sources all Beets/plugin diagnostics from `backend/beets_adapter.py` and `backend/beets_plugins.py`.
- `routes_submissions.py`: split route module for MusicBrainz/AcoustID submission workflow and MBID attachment; AcoustID submission runs through the real `beetsplug.chroma` plugin inside stock Beets via `beets_adapter.mbsubmit()`.
- `job_engine.py`: `PythonJob` and the durable `JobStore` (ARCH-004): structured state, cooperative cancellation, log retention, restart resolution, and an opt-in, in-process duplicate-start guard: a job whose metadata carries `dedupe_key` is refused while a job with the same key runs (`DuplicateJobError`, HTTP 409). The key must name the job's whole input; today only Move All and MBSync All set one. Move All fails at once with `not_supported` (see below), so for it the guard refuses a second start only in the moment before the first one fails; MBSync All runs until Beets finishes, so a second start gets 409 for its whole run. A job that returns `{"ok": false}` ends `failed`. A job ends `cancelled` only when it stopped because of the cancel: it raised `"cancelled"`, or its cancel event's `is_set()`/`wait()` returned True before it returned or raised (`job_engine.cancel_honoured`). A cancel the job never saw keeps the real outcome (`success`/`failed`) and adds a log line, and the hook-created transaction follows the same rule, so a finished mutation is never recorded Cancelled.
- `helpers_mb.py`: MusicBrainz and AcoustID helper functions. It has no `app.py` dependency and is the strongest current provider boundary.
- `backend/beets_adapter.py`: the only supported transport to stock Beets — a narrow `BeetsAdapter` client for the `web` plugin's reads and the `webmanager` plugin's authenticated mutation operations (`modify`, `move`, `remove`, `mbsync`, `mbsync_library`, `fetch_art`, `embed_art`, `lastgenre`, `mbsubmit`).
- `beetsplug/webmanager/`: the integration plugin itself, provisioned by Web Manager into stock Beets' `/config/beetsplug` and loaded by stock Beets like any other Beets plugin. Exposes `/webmanager/status` (handshake: protocol/plugin/Beets versions, loaded plugins, capabilities; from plugin 1.6.0 also Beets' own `directory`/`library` paths, the effective `allowed_roots`/`import_roots`, `web.include_paths`, and whether `fpcalc`/`ffmpeg` exist in the Beets container. These fields are additive, the protocol stays 1.0, and older plugins are reported as `unknown`) and the operation endpoints `BeetsAdapter` calls.
- `backend/`: helper package. `beets_adapter.py` and `beets_plugins.py` (plugin provisioning/health) are the stock-Beets integration surface; `album_match.py`, `audio_preferences.py`, `import_guard.py`, `mb_alignment.py`, `security.py`, `slskd.py`, `title_normalize.py`, and `transaction_engine.py` are Web-Manager-local domain/orchestration logic. The retired control-agent client `beets_client.py` has been deleted (ARCH-010, closed in v0.1.25); the composite workflows live in `backend/composite_workflows.py` on top of `beets_adapter.py`. `config_layers.py` defines the configuration layers (host, deployment, container, application) described in `docs/CONFIGURATION.md`.
- `frontend/src/`: React/Next/TypeScript frontend. `frontend/src/api/client.ts` centralizes API calls, `frontend/src/api/types.ts` centralizes response shapes, and views/features are split under `views/` and `features/`.
- `.github/workflows/`: CI covers Python syntax/unit tests, frontend typecheck/build, lint, Docker build, dependency audit, compose/security checks, stock-Beets acceptance (a real `lscr.io/linuxserver/beets` container), and production Docker acceptance.

## Intended Dependency Direction

```text
Browser
  -> Beets Web Manager routes (app.py, routes_*.py on port 8337)
  -> backend/beets_adapter.py (BeetsAdapter)
  -- HTTP, container-internal only -->
     reads    -> stock Beets `web` plugin           (:8337)
     mutations -> stock Beets `webmanager` plugin    (:8337, authenticated)
  -> stock Beets Library -> /config/musiclibrary.blb & /music
```

Both containers share these filesystem mounts:
- `/config` — Beets configuration and the authoritative SQLite library. Web Manager mounts this read/write only to provision the `webmanager` plugin's files and merge its config.yaml entries; it never opens `musiclibrary.blb` directly.
- `/music` — the target music library collection. Mounted **read-only** into Web Manager; stock Beets owns all `/music` writes.
- `/downloads` — incoming download staging folder, read/write in both containers.
- `/web-manager-data` — Web Manager's own durable state (settings, wizard completion, transaction/audit logs). Not shared with stock Beets.

## External Boundaries & Locking Model

- **Authoritative Database**: `/config/musiclibrary.blb` is opened exclusively by the stock Beets container. Web Manager never opens it directly — all reads and writes go through the `webmanager`/`web` plugins over HTTP.
- **Port Exposure**: Stock Beets' `:8337` is internal to the Docker network only, never published to the host. Web Manager's own `:8337` (`WEBCONTROL_PORT`) is the only port published, to `0.0.0.0:8337` (or `127.0.0.1:8337`) for browser access. Nothing in the current architecture uses port 8338.
- **Health and Readiness**: `/api/health` validates Web Manager liveness; `/health/ready` and `/api/setup/status` call `BeetsAdapter.get_plugin_status()`/`get_stats()` to report stock-Beets reachability, the `webmanager` plugin's protocol-version compatibility, loaded Beets plugins, and filesystem health.
- **MusicBrainz and AcoustID**: `helpers_mb.py` performs release, release-group, recording, and AcoustID lookup work. `routes_submissions.py` performs MusicBrainz validation and AcoustID submission orchestration through `beets_adapter.mbsubmit()`.
- **Submission Command Capability**: the `webmanager` plugin's `/webmanager/status` handshake reports whether `mbsubmit` (AcoustID, via the real `chroma` plugin) is available before Web Manager offers it.

## State Ownership

- **Library State**: `/config/musiclibrary.blb` is the authoritative Beets library, owned exclusively by the stock Beets container.
- **Web Manager Durable State**: `/web-manager-data` (`WEB_MANAGER_DATA_DIR`, mounted to `./web-manager` by default) holds `app_settings.json`, `.setup_complete`, `.auth_token`, and session encryption keys.
- **Job State**: `JobStore` (`job_engine.py`), durable under `<WEB_MANAGER_DATA_DIR>/jobs/<job_id>.json` when the data dir is set explicitly (every shipped Compose file) or `BEETS_WEB_DURABLE_JOBS=1`; structured progress and logs are exposed via `/api/jobs/*`.
- **Audit & Transaction State**: Stored in `backend.transaction_engine.TransactionStore` under `/web-manager-data/transactions` (`BEETS_TRANSACTION_DIR`).
- **Import Review State**: Staged under `/downloads` and tracked in `/web-manager-data/unmatched_drafts`.
- **Review Queue vs. Library missing IDs**: `GET /api/import/review-queue` lists import decisions only (Pending Review folders and skipped imports, a skipped folder already in Pending Review listed once) from Web Manager state and `beet.log` (last 8 MB). It never reads Beets, so it answers while Beets is down. It sorts the whole list (pending before skipped, newest first), then pages it with `offset`/`limit`; `total` and `counts` (`all`, `pending_ai`, `skipped`) cover the filtered list, not the page. Library albums without a Release ID and singleton items without a Recording ID are served by `GET /api/library/missing-mb-ids` (`backend/library_service.library_missing_mb_payload`): one `get_items` + `get_albums` read per call and no per-album calls; the album folder comes from the first item's path. Rows keep the `library_no_mb` shape, so `POST /api/import-review/decision` and `POST /api/import/review-folder/delete` accept them unchanged. `status=library_no_mb` on the review queue returns an empty page with `moved_to` until the next minor release.
- **Review Queue revalidation and skip ledger**: `POST /api/import-review/revalidate` answers synchronously only for an explicit list of at most 25 ids; `all: true` or more ids start one `import-review-revalidate` job (`dedupe_key` of the same name, `mutating` only with `auto_enqueue`) and return 202 with its `job_id`; the job result stores counts plus at most `IMPORT_REVIEW_REVALIDATE_JOB_ITEMS_MAX` (200) compact rows (`_compact_revalidation_summary`). The work lives in `backend/import_review_service._run_import_review_revalidation`. Folders Beets skipped during a Web Manager import are recorded in `<WEB_MANAGER_DATA_DIR>/import_skipped.json` (owned by `backend/pending_review_store.py`, atomic write); `_remove_pending_review_for_path`, which every import or resolve path calls, drops the folder from that ledger too, and never raises (a ledger failure is logged by exception type only). `POST /api/ai-pending-review` accepts only a folder under the Import Review source roots (not the library) and only identity fields from the client; evidence, confidence and status are server-computed. Where a stored entry authorizes an action (`_pending_review_matches` for folder deletes and import-with-id, the ready-items auto-import), its path is re-resolved under the approved roots (`pending_review_store._trusted_stored_review_path`; a symlink may cross into another approved root but never from outside `MUSIC_ROOT` into it) with no raw-text shortcut, so entries stored before that validation authorize nothing outside them.
- **Find Music list (acquisition queue)**: a snapshot owned by `backend/acquisition_service.py`, in memory and in `<WEB_MANAGER_DATA_DIR>/acquisition_queue_cache.json` (atomic write). Only the `acquisition-queue-build` job (`mutating: false`, `dedupe_key: acquisition-queue-build`) builds it, from the library payload plus every Lidarr wanted page (`fetch_lidarr_wanted`). Requests never build it: `GET /api/acquisition/queue` pages the snapshot (500 rows when `limit` is absent; it has no refresh argument) and, when it is missing, older than 6 h or lacks the unmonitored rows asked for, starts the job and answers at once (stale-while-revalidate; no retry within 5 min of a failed build). `POST /api/acquisition/queue/refresh` starts or joins the job. A build whose library read or Lidarr fetch failed (Lidarr not configured excepted) or was cancelled never replaces the last good snapshot; the error and age are reported in the response's `cache` block. `POST /api/acquisition/download-all` selects rows from the snapshot by key (409 `queue_not_ready` without one). A Find Music download whose import put the album into the library (the reimport job returned `album_ids`; `download_entered_library`) drops its row from the snapshot (`acquisition_queue_mark_done`; a build already running drops it too). Refresh contract: body `{"include_unmonitored"?: true, "after_download"?: true}`. Only `after_download: true` (the UI's automatic refresh after a download) may reuse the snapshot, once within 120 s of that patch: `200 {"ok": true, "job_id": null, "already_running": false, "reused": true}`. Every other Refresh, a user's click included, answers `202 {"ok": true, "job_id", "already_running", "reused": false}`. Other imports, including Lidarr's own, show only after the next build (ARCH-028).

## Job Lifecycle

Existing lifecycle:

1. Routes start Python callables through `JobStore.start_python()`.
2. `PythonJob` accepts `(log, cancel_event, update_state)` for jobs that support structured state.
3. `/api/jobs/*` serializes job status, logs, metadata, and compact results.
4. Some workflows add their own checkpoint files and resume logic, especially playlist and AI-batch/import flows.
5. There is no generic remote "run this Beets command" job abstraction — a narrow, operation-specific `BeetsAdapter` call (e.g. `mbsubmit`, `modify`) runs synchronously inside a `PythonJob`, and a job is never reported `cancelled` once stock Beets has already completed the underlying operation.
6. **Duplicate starts.** Every mutating request (POST/PUT/PATCH/DELETE) gets a start scope (`routes_jobs.py` → `job_engine.enter_start_scope`). The first job it starts records the request fingerprint (method, path, query, body, upload bytes) and the optional `Idempotency-Key` header (8–128 of `A-Za-z0-9._:-`). Responses, all with nothing started:
   - identical request while that job runs (mutating jobs only): `409 {"code": "job_already_running", "job_id", "status": "running", "replay": false}`;
   - same `Idempotency-Key` again, any status, also after a restart while the record is kept: `409 {"code": "job_already_started" | "job_already_running", "job_id", "status", "replay": true}`;
   - same key with a different request: `422 {"code": "idempotency_key_reused", "job_id"}`; a malformed key: `400 {"code": "invalid_idempotency_key"}`.
   A client that retries a start (lost response, timeout) sends the same key and follows `job_id` on a 409. A start that must be single whatever its body names a workflow or resource key, `metadata["dedupe_key"]` (`workflow:maintenance-runner`, `workflow:maintenance-duplicates`, `import-source:<path>`): `start_python` checks for a running job with that key and registers the new one under one `JobStore` lock, so racing starts cannot both pass a separate "is one running?" check (D1). The job contract (`backend/job_contract.py`), the import slot and transaction CAS guards still apply on top. Jobs started outside a request (schedules, other jobs) are not scoped.
7. **Restarts.** A job persisted as running when the process stopped is never re-run: read-only jobs become `failed`, others `recovery_required`; the row carries `interrupted: true` and `recovery` (`interrupted_at`, `last_heartbeat_at`, `checkpoint`). Resume is the workflow's own, from its checkpoint (Clean All, playlist download, AI batch).
8. **Recurring work and watchers.** `JobStore.every(name, interval_seconds, tick, initial_delay=0)` runs `tick()` on a store-owned schedule until `JobStore.close()`; the tick starts tracked jobs with `start_python` and may return the job, in which case later ticks are skipped until it finishes. `PythonJob.add_done_callback(fn)` runs `fn(job)` once the job is terminal. Neither needs an ad hoc thread.
9. **Persisted records are redacted** (`job_engine.redact_for_persistence`): `log_tail` and `result` on disk never carry `key=value` secrets, bearer tokens, sensitive dict keys or URL userinfo, whatever the producer logged (#272).

Intended direction:

- Every long-running workflow should have an operation id or idempotency key, durable progress, bounded retries, cancellation checks between safe steps, and clear terminal states.
- Jobs should orchestrate application services and checkpoint state rather than duplicate matching or mutation business rules inline.

## Matching Lifecycle

Existing entry points include:

- Import review AI and candidate flow in `backend/import_review_service.py`, `backend/ai_service.py`, `backend/ai_evidence_service.py` and `routes_import.py` (item/album/folder AI suggestion, target preview, auto-enqueue, revalidation, attach/match).
- MusicBrainz and AcoustID helpers in `helpers_mb.py`.
- Track alignment in `backend/matching/track_alignment.py` (canonical) and `backend/mb_alignment.py`.
- Import safety decisions in `backend/import_guard.py`.
- Playlist matching in `backend/playlist_service.py` around `_match_playlist_tracks`, reference matching, and quality-place flows.
- Missing-track replacement and Music Format Preferences matching in `backend/replacement_service.py` and `backend/acquisition_service.py`.
- Submission preparation and MusicBrainz validation in `routes_submissions.py`.

Intended direction:

- Converge matching entry points on one shared result contract containing local metadata, candidate identities, release-group ID, optional release ID, recording IDs, AcoustID evidence, tracklist evidence, duration evidence, filename/tag evidence, AI availability/contribution, confidence, conflicts, warnings, explanation, and action eligibility.
- Keep AI as an optional contributor, never the source of truth.

Identity evidence floors (enforced today; tests in `tests/test_identity_evidence_floors.py` and `tests/test_identity_resolver_followups.py`):

- A provider that did not answer (no key, rejected key, outage, rate limit, `fpcalc` missing) is reported as *not checked*, never as "no match". AcoustID callers that must tell the two apart use `_acoustid_lookup_cached_outcome` or `_acoustid_hits_or_none` (`None` = not checked, `[]` = answered with no result); suggestion responses carry `acoustid_status` (`not_configured` / `auth_failed` / `lookup_failed` / empty), `acoustid_unavailable` and `musicbrainz_unavailable`.
- Merging an imported missing-track fill into an existing album needs an AcoustID confirmation of the requested recording for every file. A weak, ambiguous, unanswered or empty lookup, a MusicBrainz failure, or a file with no requested track sends the album to Review with its rows kept; nothing is deleted.
- When the AcoustID top tier names both the requested recording and a different one, the result is review (`acoustid_ambiguous`), not a mismatch.
- The import/reimport resolver (`library_service._resolve_album_release_for_import`) never sets album identity from a MusicBrainz text search alone: without a source folder to verify against it refuses, and a folder-backed search result must pass the folder preflight (`action_allowed`). A Release Group input is checked against at most `_RG_ALTERNATIVE_RELEASE_CAP` (25) of its Releases closest by track count, and a failed Release Group lookup fails closed.
- `release_selected_by_operator` is passed only where the operator picked a Release that may move the album to another Release Group (manual match); paths that already verified the Release is in the album's own Release Group do not pass it.
- With `fingerprint_evidence=True` (only `identify_import_folder` passes it), `_folder_release_preflight` attaches each local file's AcoustID hits (`acoustid_hits`) to the tracks it hands the canonical evaluator, so fingerprints can prove tracks. The key is set only for an answered lookup; an unanswered one stays absent and reads as *unavailable*. Other callers keep the default (no hits attached). In folder identification, Stage 2b auto-import is blocked by an unanswered release lookup, by an embedded Release ID that was not evaluated (`embedded_release_not_evaluated`), and by a competing Release Group that could plausibly be the folder's identity.
- Competing-proof rule (`folder_identity.could_be_folder_identity`): another Release Group blocks Stage 2b (`other_release_group_has_track_proof`) when its coverage is at least half of the folder's audio files (`2 * coverage >= audio_files`, coverage > 0). Its coverage is the larger of the proven tracks of its best evaluated release and the number of files whose confirmed fingerprint names the group. The winner must prove every file, so a group under half (an album track that is also on a single or a compilation) is not evidence for that group and does not block. A fingerprint-named group that was never evaluated is counted at its fingerprint files plus every file without a confirmed fingerprint, and blocks (`fingerprint_group_not_evaluated`) if that reaches half. Two groups that both pass `can_auto_accept` always block (`multiple_release_groups_verified`).
- Folder identification walks the resolved folder recursively without following links, and keeps symlinked or junction audio files out of the evidence, as `_build_folder_evidence` does. It still looks inside every symlinked or junction directory, with a loop guard, because Beets' importer walk (`beets.util.sorted_walk`) follows them. Any audio file that is a link, or that sits under a linked directory, would be imported without proof, so it is a hard conflict (`symlinked_audio_file`) and the folder goes to review. A linked directory holding any file, and any linked file whatever its extension, also counts, because Beets decides what is audio by reading the file, not by its name; only an empty linked directory does not block.

Deterministic import identification (0.6.0; tests in `tests/test_import_folder_identity.py` and `tests/test_library_identity_gaps.py`):

- `backend.import_identity.identify_import_folder(folder, skip_reason)` identifies a folder Beets skipped, without AI and without writes. It seeds releases from embedded IDs, from Release Groups and Releases confirmed by AcoustID, and from MusicBrainz text search. It runs `_folder_release_preflight` on each release, then groups the results by Release Group. The ranking rules are pure functions in `backend/matching/folder_identity.py`. The result's `auto_import.eligible` is the Stage 2b gate. It holds only when all of these are true:
  - exactly one Release Group passes `can_auto_accept(VERIFIED_SUBSET)`;
  - no other Release Group could plausibly be the folder's identity (the competing-proof rule above), every embedded Release ID was evaluated, and no release lookup failed;
  - there is no hard conflict, such as an embedded Recording ID contradicted by a fingerprint, or an embedded Release Group that differs from the candidate's;
  - every file is proven by a confirmed fingerprint or a matching embedded Recording ID;
  - the skip reason is not `duplicate`.

  The caller must still require a Beets strong match and exactly one new album with the planned Release Group (`post_conditions`). `ai_rank` is always `null` there.
- `backend.matching.library_identity_gaps(albums, items)` is the pure membership rule for "Library: missing IDs". Album identity is keyed on `mb_releasegroupid`, so a Release ID without its Release Group is a gap. Only well-formed UUIDs count as IDs.

## Mutation Lifecycle

Existing mutation mechanisms include:

- Narrow, operation-specific `BeetsAdapter` methods (`modify`, `move`, `remove`, `mbsync`, `fetch_art`, `embed_art`, `lastgenre`, `mbsubmit`) — the only way Web Manager reaches a stock-Beets mutation. The web-manager container never shells out to `beet` locally and never runs a local Beets Python runtime (enforced by an AST-based structural test, `tests/test_arch003_boundary_enforcement.py`).
- `modify` stores only fields this Beets version has (webmanager plugin 1.11.0). Web Manager reads and edits `genre`. On Beets 2.13 and later, which replaced it with the multi-valued `genres` field, the plugin maps `genre` to `genres`, splitting the string the same way Beets' own genre migration does, and the adapter derives `genre` from `genres` when reading. Older Beets keeps `genre`. The plugin refuses any other field Beets has no column for with `400 UNSUPPORTED_FIELDS` before writing anything; only `data_source`, which Beets itself keeps as a flexible attribute, is exempt. A file-tag write failure answers `500 WRITE_FAILED` with the item ids, so the apply fails instead of reporting the fields as written. With `write`, an album update also writes its tracks' tags, as `beet modify -a` does.
- A file-backed `TransactionStore` in `backend/transaction_engine.py` (plan/apply/verify/recover) with statuses, changes, metadata diffs, rollback fields, and job attachment. This bookkeeping is pure Web-Manager-local orchestration; it does not itself talk to Beets.
- Rollback eligibility is server-owned (#228): `GET /api/transactions` and `GET /api/transactions/<id>` add `rollback.allowed` (bool), `rollback.allowed_code` (`allowed`, `not_applied`, `already_rolled_back`, `not_supported`, `unavailable`, `unsupported_operation`, `not_completed`) and `rollback.allowed_reason` (empty when allowed), computed by `routes_maintenance.rollback_eligibility` from the same gate `POST /api/transactions/<id>/rollback` applies. `rollback.available` and `rollback.reason` stay the stored values. An engine rollback that ran but failed verification (status Recovery Required) answers with `mutated: true`.
- Several workflow-specific preview/dry-run routes, including import target preview, cleanup scans, folder placeholder preview, and transaction endpoints.
- Transaction audit and recovery rules (0.4.0):
  - A step's log lines are appended (`TransactionStore.update(..., append_logs=[...])`); `logs=` replaces the whole log and is used only by job wrappers that pass the job's full log. No later step, refusal or recovery erases the record of what an apply did.
  - Rollback eligibility checks each family's own evidence key (quarantine, merge, record, art id, relocation `after`, album-metadata `before_state`); a rollback-only family is eligible only when Completed, Failed or Partially Rolled Back. A Partially Rolled Back folder cleanup or local metadata rollback can be retried: each restore is idempotent.
  - A one-shot plan -> approve -> apply that raises before its claim (a busy or stale lock) ends Cancelled, never Approved with nobody to apply it (`resource_locks.cancel_unclaimed_on_error`).
  - The startup sweep (`backend/transaction_recovery.py`, Waitress runs one process) resolves Running transactions last written before the process started: registry and manifest families from Beets' durable records; a claimed composite apply, a folder cleanup or an import-review cleanup to Recovery Required; a library sync with a recorded Beets operation id to Recovery Required with a cancel action; a job wrapper follows its job (`recovery_required` maps to Recovery Required). A transaction the sweep completes or fails says so in its own log. A Running wrapper with no evidence is left as is.
  - Staging files (downloads, quarantine) move fd-relative from their staging root and never replace an entry that appears at the target after the check: a file is hard-linked then its old name unlinked, a directory is renamed over an empty placeholder made with exclusive `mkdir`; across filesystems a file is copied, fsynced and its source unlinked only when its identity, size and mtime are unchanged. A staging delete refuses a folder that holds another mount.
  - Failure injection between stages (after preview, mid-apply, after a file step but before its result is recorded, a process crash mid-apply, and during rollback) is covered for the folder cleanup engine in `tests/test_failure_injection_matrix.py`, and for album moves in `tests/test_album_relocation_transaction.py`.

Intended direction (the target shape for every production mutation path):

1. Inspect current state (via `BeetsAdapter` reads).
2. Produce a mutation plan.
3. Validate roots, identities, conflicts, and preconditions.
4. Display or record metadata and filesystem diffs.
5. Apply through `BeetsAdapter` calls with audit records.
6. Verify final state (via `BeetsAdapter` reads).
7. Record completed steps and recovery information.

Current migration status: every Beets read and mutation path, including the composite workflows (merge-album, merge-artist, Clean All, track replacement, folder/album cleanup, artist-folder reconcile, album maintenance/relocation/metadata-repair, artwork, genre repair), runs through `backend/composite_workflows.py` and `backend/beets_adapter.py`. Not all of them have an operator-reviewed preview or a rollback. Album rename (`POST /api/albums/<id>/rename`) and move-to-library (`POST /api/albums/<id>/move-to-library`) use the album move family (`album_move_v1`, plugin 1.14.0, capability `album_relocation`); so do the other jobs that call `composite_workflows.relocate_album` (normalize/merge artists, duplicate resolver, attach and retag relocation). The plan records each track's path, the album folders and the cover path. **The operator's click is the approval**, as for artwork: there is no separate review step, and the request is recorded as `approved_by: "operator album rename"` (or `"operator album move"`). The apply records its engine request first, holds the album's resource lock, and calls `POST /webmanager/album-relocation`, where Beets' own `Album.move()` moves the files and cover to where its path templates put them; the plugin refuses (`STALE_PLAN`, nothing moved) unless the album still has exactly the planned tracks at the planned paths, puts back what it moved if the move fails part-way (`UNDONE`), and returns every path before and after, which Web Manager checks against live Beets. Beets' `Item.move()` skips a track whose file is missing with only a warning: the plugin reports `moved` and `skipped` track ids, and a partial move is recorded as Failed with that list (still rollbackable; the rollback moves back only the tracks that moved). Beets' `move_art` clears `artpath` when the cover file is missing; the recorded old `artpath` is put back by the rollback. Each operation records exactly one transaction (the jobs opt out of the job-hook row). `POST /api/transactions/<id>/rollback` calls `POST /webmanager/album-relocation/rollback`, which moves each file back with Beets' `Item.move_file()` and the cover with `util.move` (no overwrite), each file move and its row store in one Beets transaction, and checks every path afterwards: a `util.unique_path` rename (`name.1.ext`, the old path taken meanwhile) is a failure that is put back, never accepted. A track already at its old path counts as done, so a retry after a restart resumes from the recorded paths instead of replaying. A crash between Beets' file move and its row store (the apply records each file's size and mtime as evidence) leaves the row at the moved path with no file and the untracked file at its old path: a retry adopts it, storing the row without moving anything, only when size and mtime match; anything unprovable is refused (`file_missing`) and nothing is overwritten. Web Manager records `rollback_request` with no outcome before the call: a Beets that does not answer, a refusal after an interrupted attempt, or a Web Manager restart with an outcome-less request (restart sweep) leaves the transaction Recovery Required, never Completed. Restart recovery of an apply proves "nothing changed" only when the rows AND the files are still at the planned paths. Vacated folders are removed only when empty with `os.rmdir`, never `util.prune_dirs`. Moves stay within one filesystem in a normal layout (`os.replace`, owner and mode kept); across filesystems Beets copies mode and times but not the owner, and nothing chowns. Every check runs before anything moves; it refuses with HTTP 409 and changes nothing when the album is gone (`album_not_found`), its tracks changed (`album_changed`), a track was moved again (`item_moved`), the cover changed (`art_changed`), a moved file is gone (`file_missing`) or an old location is occupied or tracked (`target_exists`), and with 400 for a restore path outside the allowed roots, through a symlink, or with another extension. A restart mid-apply is resolved from Beets' durable operation record and the recorded paths (`backend/transaction_recovery.py`): unchanged paths prove nothing moved (Failed), an engine success is verified and recorded, anything else is Recovery Required; it is never replayed. A preserved torrent source is never moved (#332, plugin 1.15.0, capability `album_relocation_link`): the plan applies the shared torrent-source rule (`library_service._preserve_torrent_source_file`: the file's folder or any folder up to the torrent root is preserved, as for rejected downloads in #321; when it cannot be evaluated the file is treated as preserved) to every track and the cover, and records `operations` (`move`|`link` per track) and `art_operation`. A plan with any `link` is applied only when `GET /webmanager/status` lists `album_relocation_link`; an older plugin ignores the field and would move, so the apply is refused first (`plugin_outdated`, Failed, nothing changed). The plugin runs Beets' `Album.move()` steps itself, per track: `Item.move(MOVE)` for `move`, and for `link` `Item.move(HARDLINK)`, then `Item.move(COPY)` when Beets' `util.hardlink` raises `FilesystemError` (EXDEV across filesystems or Docker volumes, EPERM under `fs.protected_hardlinks`, no link support); the cover goes through `move_art()` the same way. It reports `methods` (`moved`|`linked`|`copied`) and `art_method`, and its evidence holds [size, mtime, dev, inode] of every original and of each library file it made. The rollback never moves a linked or copied file: it proves the original unchanged at its old path (same dev, inode, size and mtime; otherwise `source_changed`) and the library file to be the one this move made (the original's inode for a link, else the recorded library evidence; otherwise `library_file_changed`), stores the row back on the original, and only after every row is final unlinks that library file, re-checking that it is still ours, untracked, strictly inside the Beets library directory, and that the original still exists; the unlink walks from the library directory with `O_NOFOLLOW` directory fds and re-checks the inode right before `unlinkat`. Methods, paths and evidence come only from the plugin's own durable record of the apply (`apply_operation_id`, its Idempotency-Key, kept 7 days and at most the last 1000 operations), never from the rollback request. A successful rollback marks the record rolled back, so a replay (any key) proves nothing and removes nothing. Without a valid record (expired, unknown, another album's, failed, or rolled back) a linked or copied track or cover is never pointed back: the rollback refuses with `RELOCATION_RECORD_MISSING` and both files stay; a moved track only goes back by a real move to a safe, free restore path (payload size/mtime never adopt a file). A link or copy that fails after creating its file (a partial copy, a failed row store) removes that file when its name was free before. A library file already gone is not an error; one that cannot be proven at unlink time is kept and listed. A retry after an interrupted rollback (rows already on the originals) only removes the library files. A failure part-way through the apply points linked/copied rows back and removes their library files before reporting `UNDONE`. Restart recovery of an apply that died after a link or copy but before its row was stored still reads "nothing changed" from the rows and originals; such an untracked library file is left in `/music`. Before any tag write the plugin breaks a hard link (copy-on-write): on Beets' `write` event, which every `Item.write`/`try_write` sends first (Web Manager tag edits, MBSync All, embedart's embedded art, genre fixes, even `beet write` inside the container), a file with more than one link is replaced by its own copy in the same folder (mode, owner when allowed and times set on the open copy's descriptor, both names re-checked by inode, then `os.replace`), so the write never reaches the torrent's bytes; if the copy cannot be made the write is skipped and logged. Beets never hard links on import (plugin 1.8.1 turns `link`/`hardlink`/`reflink` off), so breaking any library file with more than one link is safe. Covers are never written in place: `Album.set_art()` removes the old name and copies a new file. Tools that write tags without Beets (`beet scrub`, an external tagger) are not covered. `after_write` refreshes the library evidence in the relocation record only for the same item id and only when the file just before the write (noted by the `write` listener) was the one the record proved ours (only in the Beets process serving Web Manager; any webmanager request loads the registry after a restart), so the rollback still proves and removes the copy; after a `beet write` from the command line the copy is unproven and the rollback refuses with `library_file_changed`. The torrent-source rule runs in Web Manager on Beets' paths, so the downloads folder must be mounted at the same path in both containers; under another path the rule cannot match and the files move. Records of the older `album_relocation_v1` family hold no paths and stay non-rollbackable. The library-wide Move All (`POST /api/library/move-all`) is not a workflow: it starts a job that `composite_workflows.move_library` refuses with `not_supported`, so the job fails and nothing in the library changes. MBSync All (`POST /api/library/mbsync-all`, `mbsync_library_v1`, plugin 1.13.0, capability `mbsync_library`) runs Beets' own mbsync inside Beets: the job calls `composite_workflows.mbsync_library`, which starts `POST /webmanager/mbsync/library` and polls the plugin operation. The plugin calls the loaded `MBSyncPlugin.albums()`/`singletons()` once per album with an `mb_albumid` and per singleton with an `mb_trackid` (the targets `beet mbsync` visits), holding its `mutation_lock` for one album at a time. It never moves files: it passes `move=False` whatever `import.move` says, because a move needs the old paths recorded and moving files is the relocation workflow's job. Tag writes follow Beets' `import.write` (`ui.should_write()`), but mbsync itself runs with `write=False`: Beets' `apply_item_changes()` ignores the result of `Item.try_write()`, so a failed write would pass silently. The plugin calls `Item.try_write()` on each item mbsync changed, stores the new mtime when it worked, and lists the item under `write_failed` when it did not (its database fields did change). Web Manager does not talk to MusicBrainz for it. Its only custom code reads each target's stored fields before and after the call, so the transaction can list what Beets changed (the first 200 changed albums or singles, values cut to 120 characters; counters cover everything), and counts the targets mbsync skipped: `skipped_no_id` (no MusicBrainz ID) and `not_found` (MusicBrainz answered but has no such Release/Recording, so mbsync never opened its per-album library transaction; such a target is not also counted unchanged). A failed lookup is not "not found": with Beets' default `raise_on_error: no`, `metadata_plugins.maybe_handle_plugin_error` catches the source's exception, logs "Error in '<source>.album_for_id': ..." (or `track_for_id`) and returns None, so the plugin attaches a logging handler to the `beets` logger for the duration of each target's mbsync call that records only that message from its own thread. A target with such a lookup error, or one that raises, is recorded under `failed` and the sync goes on. A tag write that raises instead of returning False is recorded under `write_failed` with the error, and the sync goes on. When any target failed or any tag write failed, the job and transaction end Failed with `MBSYNC_PARTIAL` and the counts; every other target keeps its changes. It has no preview and no operator review: the button's confirmation is the approval. Beets keeps no undo, so the transaction records `rollback_available: false` with that reason and `POST /api/transactions/<id>/rollback` refuses it (HTTP 409); tags already written stay written. Only one library sync runs: the job's `dedupe_key` gives 409 `job_already_running`, and the plugin answers 409 `ALREADY_RUNNING` to a second start from anywhere. Cancelling the job (`POST /api/jobs/<id>/kill`) sends `POST /webmanager/mbsync/library/<id>/cancel`; Beets stops after the album it is on, the albums already synced keep their changes, and the job and transaction end Cancelled. A cancel that reaches Beets after it finished leaves the real outcome. If Beets restarts mid-run the sync stops there and the job fails with `operation_lost`. Ten albums in a row that fail (a lookup error while MusicBrainz is unreachable or rate limiting, for example) stop the sync with `MBSYNC_ABORTED`. The retired `backend/beets_client.py` control-agent client is deleted (ARCH-010, closed in v0.1.25). `backend/transaction_engine.py` now holds only the TransactionStore, folder cleanup and import-review cleanup; the engine-side families that opened the Beets SQLite library directly were removed (BA-7), and folder cleanup checks Beets references through the adapter. Folder cleanup (`folder_cleanup_v1`: Clean All folder-safe renames, merges and empty-folder removal) never writes `/music` from Web Manager, which mounts it read-only: Web Manager plans, approves, audits and rolls back the transaction in its store, and each filesystem step (`move_file`, `rename_dir`, `remove_empty_dir`, `create_dir` for rollback) is one `BeetsAdapter.folder_op` call to the plugin's `POST /webmanager/folder-op` (plugin 1.7.0, capability `folder_op`). The plugin confines every path to the Beets library `directory` with no symlink component, refuses paths that hold library items (those move only through Beets' `item.move()`/`album.move()`), never re-creates a path Beets still references, never overwrites, and holds the plugin's `mutation_lock` and a library transaction. It uses Beets' `util.move` and `util.mkdirall`; an untracked folder rename uses `os.rename` (Beets has no API for it), and empty-folder removal uses `os.rmdir` rather than `util.prune_dirs`, which in Beets 2.13/2.14 checks emptiness and then calls `shutil.rmtree`, so it could delete a file created in between. Only an Approved transaction applies. Each confirmed step is recorded in `engine_result` as it happens. A step whose reply is lost is replayed with the same idempotency key, which makes the plugin report the original outcome; a step still unconfirmed after that is recorded too (rollback checks the filesystem before undoing it). A step that fails or cannot be confirmed leaves the transaction Failed with what already changed, and the generic rollback route (`POST /api/transactions/<id>/rollback`) undoes a Completed or Failed folder cleanup. Operator artwork (upload and "replace from URL", `album_art_replace_v1`, plugin 1.12.0, capability `album_art`) follows the same split: Web Manager validates the image, fetches a URL only through `provider_boundary.opened_public`, plans the `Artwork Update` transaction, records the operator's request as its approval and sends the image bytes to `POST /webmanager/album-art`. The plugin uses Beets' own `Album.set_art()` (file named by `art_filename`, `artpath` set, `art_set` sent so a loaded embedart embeds it exactly as after fetchart), confined to its allowed roots. Its only custom code is the snapshot it takes first, because Beets has no undo: the previous cover, any file at the new cover's name and each track's embedded images go into its quarantine folder with a manifest. `POST /webmanager/album-art/rollback` restores them from that manifest (never from caller paths) and refuses when the album's art changed since.

### Import contract

Every import is Beets' own importer run inside stock Beets by the `webmanager` plugin's `POST /webmanager/import` (`BeetsAdapter.run_import`). Web Manager never tags, matches or places files itself during an import; it only chooses the source, the copy/move mode and, when a person confirmed one, the MusicBrainz Release, and then verifies the result over the read API.

| Route | Composite | Beets equivalent |
|---|---|---|
| `POST /api/import` | `reimport_source()` | `beet import -q` with `autotag: yes`, `quiet_fallback: skip` always (a request with `fallback: asis` is run as `skip` and reports `asis_refused`, so an album with no verified identity is left in place for the Review Queue, never imported with blank or placeholder tags), `--search-id` = the optional `search_id` |
| `POST /api/folders/import-with-id` | `plan_confirmed_import()` / `apply_confirmed_import()` | `beet import -q --search-id <mb_albumid>` with `quiet_fallback: skip` |
| `POST /api/albums/reimport-disk` | same confirmed-import family | same; a folder inside the library is imported in place (no copy, no move) |
| `POST /api/ai-batch-import` (the batch import; the name is historical, it never calls AI) | per folder: `reimport_source()`, then for a skipped folder `identify_import_folder()` and, only when `auto_import.eligible`, the confirmed-import family | Stage 1 is `beet import -q` of that one folder with `quiet_fallback: skip`; Stage 2b is `--search-id <release>` |

- `/api/import` is an API-only whole-tree import (one `beet import -q` over the source, 300 s default timeout). The Import page uses the batch import, which runs one folder at a time inside one `job_engine` job and keeps a durable per-folder state (pause, skip, stop, recover).
- Batch import stages (0.7.0, #288). Stage 1: Beets' quiet import of the folder; every album it reports (plugin 1.16+ `imported_album_ids`) is recorded in History once, and an album without `mb_releasegroupid` is set to `review_required` (`missing_release_group_album_ids`), never repaired through `mb_albumid`. A partial import (Beets skipped some paths) gets one review row whose evidence lists `skipped_paths` and the kept `album_ids`. Before Beets runs, `ai_service._ai_batch_preimport_check` finds the configured import root the folder lives under (`_import_review_cleanup_roots(allow_music=True)`); links at or above that root (a symlinked mount) are allowed, a symlink or junction in the path below it is a hard conflict `symlinked_audio`, and so is any linked file or linked non-empty directory inside the folder. A folder outside every configured root, a folder or subfolder that cannot be listed (`_recursive_audio` fails closed), and a folder with no readable audio go to review as `unverifiable_folder`. Beets never sees any of them. If any audio file has `st_nlink > 1` (hardlinked, e.g. a seeding torrent), Stage 1 and the Stage 2b pinned import copy instead of move. The check runs before the Beets import, not inside it, so a link swapped in between is not caught (SEC-004 in `docs/TECHNICAL_DEBT.md`). Stage 2: a folder Beets skipped is identified deterministically (`identify_import_folder`, MusicBrainz plus AcoustID) and gets one Review Queue row whose evidence carries `origin_step: beets_skip`, `beets_skip_reason`, `deterministic_decision` and `ai_rank: null`. Stage 2b: only when the identity engine says `auto_import.eligible` (complete fingerprint proof), the folder is re-imported pinned to that Release and the new album's Release Group is read back; any failure, including a mismatch, goes to review with the kept `album_ids`. AI is never called by the batch. Without Beets fingerprinting (`chroma`/`fpcalc`) or an AcoustID key the batch still imports Stage 1 strong matches, and the batch `warnings` and the folder's `warnings: ["imported_without_fingerprint"]` say so. Sources are moved unless they are preserved torrent sources, which are copied.

- Copy or move: a preserved torrent source (see `DOWNLOADS_ROOT` / `TORRENT_SOURCE_ROOTS` / `ALLOW_TORRENT_SOURCE_MOVE` in `docs/CONFIGURATION.md`) is always copied. `/api/import` copies unless `move: true` (a move from a preserved source is refused with HTTP 400); import-with-id moves when `move: true` was requested and the source is not preserved, and always moves an app-staged partial-import subset; reimport-disk moves download sources that are not preserved.
- Confirmed import verification: the Apply reads the albums carrying the planned Release ID before and after the import. Exactly one new album row must appear, and when a Release Group was confirmed its `mb_releasegroupid` must equal it. Zero rows means Beets skipped the folder (no confident match, or a duplicate with `duplicate_action: skip`) and the result is `not_imported`, which reimport-disk sends to review. Every outcome leaves the transaction Completed or Failed, never Preview.
- Unmatched albums: `skip` is the default on every route, because `asis` imports an album Beets cannot match with its existing tags and no `mb_releasegroupid`. Ambiguous identity goes to review instead, so whatever Beets skipped stays in place. The `/api/import` job result lists it under `not_matched` as "not matched; left in place for review". The list comes from the plugin's `skipped_paths` when the plugin reports it. Otherwise the whole source is listed when no album was added, and `not_matched_known: false` flags a partial import whose skipped folders the plugin did not name. Plugin 1.10.0 also returns `skipped`, one `{path, reason}` per folder, where `reason` is `no_candidates` (Beets found nothing, or the metadata source was unreachable), `no_strong_match` or `duplicate`. Each row carries that reason (`not_matched` from an older plugin). Because the plugin runs the importer without a Beets import log, `beet.log` never names these folders, so Web Manager records them in `import_skipped.json` under `WEB_MANAGER_DATA_DIR`. The Review Queue's Skipped source lists them with the `beet.log` skip lines: one row per folder, and the next `/api/import` of the same source replaces that source's entries, so a re-import never duplicates a row and a folder that imported drops out.
- No retag after the import: Beets applies the confirmed Release (tags, file placement, tag write), so import-with-id, reimport-disk and the batch import do not run `_match_tracks_from_mb`, `plan_album_mb_track_repair` or `relocate_album` afterwards. Both routes require the Release Group before importing and pass it to the plan, so the Apply verifies it. A reimport-disk that fills missing tracks merges the new album onto the existing one (`import_reconciliation`) and then checks that the merged album carries the Release and Release Group. An explicit `albumartist` override on reimport-disk is still applied, with a rename.
- The confirmed Release is imported as confirmed: import-with-id and the batch import's Stage 2b pass the operator's (or the identity engine's fingerprint-proven) Release to Beets unchanged. They never swap a single or EP for an album Release in another Release Group.
- The AI album suggestion surfaces the selected candidate's Release and Release Group unchanged.
- reimport-disk keeps the confirmed Release Group or goes to review. When the provided Release fails the folder tracklist preflight (and no manual override was sent), it may be replaced only by a Release of the same Release Group that passes the preflight. Otherwise the folder goes to review. A provided Release or Release Group never falls back to the free MusicBrainz search; input that cannot be resolved inside its own Release Group goes to review.
- import-with-id follows the same rule: a provided Release Group that resolves to no Release passing the folder preflight, a Release outside the selected Release Group, an unknown Release Group, or a source Beets skips as `not_imported` fails the job and queues one review item carrying the provided ID (`provided_mb_id`) and the real reason (unless the request set `queue_review: false`).
- Folder preflight artist evidence: only a source inside the library (Artist/Album layout) uses its parent folder name as the artist. A download or staging parent is a container, not an artist, and never raises `artist_conflict`. A refused preflight logs its real reason: the tracklist count when the tracklist failed, otherwise the identity decision's conflicts and missing AcoustID evidence.
- Verification failures keep the rows: when Beets imported but verification fails (`release_group_mismatch`, `import_ambiguous`, a rejected AcoustID check of requested missing tracks, a merged album without the Release), the job fails and the folder goes to review with the kept album_id in the reason, and the Failed transaction records it as `engine_result.kept_album_ids`. The rows Beets created stay in the library. Nothing in the import job removes them; a removal goes through the album cleanup preview/approve flow.
- Errors: plugin refusals map to stable codes (`autotag_not_allowed`, `path_not_allowed`, `source_not_found`, ...) with an operator message; the upstream body is never forwarded.
- Plugin requirement: the plugin must accept `autotag: true` with `search_ids` and `quiet_fallback`, report the folders Beets skipped as `skipped_paths`, and run Beets' quiet terminal import session. Plugin 1.8.0 and later do; an older plugin refuses `autotag` (`AUTOTAG_NOT_ALLOWED`), so every import route fails cleanly with `autotag_not_allowed` until the `beets` container is restarted on the current plugin.

## Frontend Architecture

- `frontend/src/app/*/page.tsx` files are thin route entries.
- `frontend/src/views/` contains major page shells such as Import, Library, Jobs, Playlists, Submissions, Clean, Config, and System.
- `frontend/src/features/` contains feature panels and larger workflow UI.
- `frontend/src/api/client.ts` centralizes API calls and CSRF header handling.
- `frontend/src/api/types.ts` defines many API response types.
- Existing large UI modules remain, including Import Review, Jobs, Playlists, and Library. These should be split only in behavior-preserving slices with tests.

Frontend direction:

- Keep UI compact and on the existing stack.
- Display evidence, conflicts, and backend action eligibility rather than recomputing authoritative identity or mutation decisions in components.
- Keep destructive actions explicit and visibly tied to evidence and confirmation.

## Areas Still Being Migrated

- Thick route handlers that still orchestrate workflows inline instead of calling their service (ARCH-001, narrowed after `app.py` was decomposed in v0.1.31).
- Job idempotency and checkpoint consistency across all long-running workflows (ARCH-004).
- Consistent provider-adapter contracts for AI, MusicBrainz, AcoustID, Plex, and download providers (ARCH-006).
- Outbound HTTP goes through `backend/provider_boundary.py`, using one of two entry points with the same policy, retries, classification and health record:
  - `opened(provider, request, ...)` is for operator-configured endpoints and fixed provider APIs. It connects with `urllib.request.urlopen`, which `backend/security.py` replaces with the allowlist-aware `secure_urlopen`. That operator path resolves each hop once, checks every answer and connects the socket to a checked address (no DNS-rebinding window), never uses a proxy, and admits public addresses, `BEETS_OUTBOUND_ALLOWLIST` entries (operator-only; each entry still requires private/CGNAT/ULA/loopback addresses), and the calling provider's own configured URL (`provider_boundary.CONFIGURED_URL_SETTINGS`, resolved by `configured_url`): one exact scheme+host+port rule, for that provider's call only, only for private/CGNAT/ULA addresses, with cross-origin redirects refused. A caller sending a URL that is not the configured one passes `trust_configured=False`. A refusal carries `hint` naming the `host:port` entry (`provider_boundary.allowlist_hint`). Cloud-metadata addresses are refused on every path.
  - `opened_public(provider, url, *, timeout, headers, max_bytes)` is for any URL supplied by a user or a provider response: the reference URL, and artwork image URLs. It connects only through `backend.security.open_public_url`, which allows public addresses only, ignores the allowlist, pins the connection to the validated address and re-validates every redirect hop. Its body has no path to `urlopen`.
  - There is deliberately no pluggable opener. That design let a user URL flow into `urlopen`, which CodeQL flagged as #1351/#1352.
  - An outbound-policy refusal is classified `rejected` and never retried.

Matching and identity: every production final identity/safety decision goes through `backend/matching/` (enforced by `scripts/audit_arch002_callers.py`). Album identity is the Release Group everywhere (`docs/arch009_identity_fields.md`).

See `docs/TECHNICAL_DEBT.md` for the full current list, including affected areas, risk, and desired state for each.
